# Generate, break, harden and certify legged policies

The strongest design for a 2025-2026 real-to-sim robustness platform is a closed loop built around a single validated scenario space. Natural language, photos and numerical optimizers all write into that space. A budgeted search then finds both the worst-case failure and the full range of distinct failure types. Margins are measured with controlled bisection rather than one-off pushes. PPO is fine-tuned on a replay mix of discovered failures, with the adversary kept bounded. The platform ends by issuing a readiness report that states confidence bounds and the search budget behind every "no failure found". Every stage can run on a CPU because the expensive object is a low-dimensional parameter vector (terrain, friction, payload, motor strength, latency, sensor noise, pushes) evaluated with short MuJoCo rollouts. The only GPU-scale step is training a policy from scratch, which the platform avoids by fine-tuning. Three features are novel against current literature. The first is an LLM acting as a red-teamer over *physical* scenarios for legged robots: the research found ERT, Q-DIG and ChatScene, but no locomotion equivalent. The second is a quality-diversity "failure atlas" fed straight back into training. The third is HORIZON-style hardening that widens randomization only inside the policy's recoverable boundary. The existing `breakpoint/scenario.py` already has the hardest architectural piece: a clamped schema with a `json_schema()` for LLMs and a normalized `severity()`. The remaining work is mostly search, statistics and training glue around it. One caveat applies throughout. Most sources were read as abstracts and summaries, and no paper benchmarks CEM, CMA-ES, Bayesian optimization (BO) and RL adversaries head-to-head on the same locomotion policy, so the method rankings below are reasoned recommendations, not measured ones.

## A clamped schema lets words, photos and optimizers share one scenario space

The 2023-2026 language-to-simulation literature agrees on one point. Free-form LLM code is unreliable, and what makes generation work is validation by execution. In Eurekaverse, an LLM writes heightfield generators for quadruped parkour, and **only just over half of GPT-4o's terrains passed the environment check**. Failures came from mis-scaled heights, out-of-bounds indexing and hallucinated helper functions ([Eurekaverse](https://arxiv.org/pdf/2411.01775)). ChatScene hit the same wall in driving: LLM-written Scenic code called APIs that do not exist. It fixed this by assembling scenarios from a retrieval database of known-good snippets ([ChatScene](https://arxiv.org/html/2405.14062v1)). GenTe goes furthest toward safety. Its vision-language model (VLM) uses function calling to compose text *and images* into terrains from a fixed atomic library of geometric and physical primitives, and it ships a 100-terrain benchmark ([GenTe](https://arxiv.org/html/2504.09997v1)). The lesson for a small project is to make the LLM *select and parameterize* primitives inside a schema, never write simulator code.

`breakpoint/scenario.py` already follows this pattern. `Scenario.from_dict` clamps every field to `BOUNDS`, and `json_schema()` can go directly to any LLM's structured-output or tool-calling mode. Three upgrades would bring it up to the state of the art. First, terrain should become a composable list of primitives (stairs, gap, slope, rough patch, each with bounded parameters) instead of one enum, so that "icy ramp followed by stairs" can be expressed. Second, schema validation should be followed by a physical check, as in Eurekaverse: the MJCF compiles, the robot spawns without interpenetration, and a zero-action rollout runs N steps without NaNs. Third, the pipeline should borrow GRS's repair loop. GRS writes a test suite for each generated simulation and routes runtime errors back to the LLM for repair ([GRS](https://arxiv.org/html/2410.15536v1)). Here the validator's error string goes back to the model up to k times, and the pipeline then falls back to a deterministic keyword parser ("icy" maps to low friction, "stairs" maps to the stairs primitive) that emits the same schema. Downstream code then never knows whether an LLM was involved, which keeps the platform runnable offline. Accepted scenarios should go into a library that serves both as few-shot context, as GenSim does with its verified task library ([GenSim](https://arxiv.org/pdf/2310.01361)), and as a regression suite.

Generated parameters also need *grounded* bounds, not only engineering bounds. DrEureka first rolls out the initial policy under perturbed physics. This builds a Reward-Aware Physics Prior: for each parameter, the range in which the policy still succeeds. The LLM then proposes domain-randomization (DR) distributions only inside those ranges. On a Go1, the result beat human-designed reward and DR by **34% in forward velocity and 20% in distance travelled** on real terrain. Ablations showed that the prior is crucial, and that LLM-chosen distributions beat uniform sampling within the same ranges ([DrEureka](https://arxiv.org/html/2406.01967v1)). A cheap version of this prior is a one-factor-at-a-time sweep per `BOUNDS` key. That sweep is the same computation as the breaking-point measurement below, so it costs nothing extra.

Image input should stay lightweight. Full real-to-sim reconstruction is now feasible, but it is heavy and aimed at manipulation. Examples are Gaussian-splat-plus-mesh twins optimized through differentiable MuJoCo ([Splatting Physical Scenes](https://arxiv.org/abs/2506.04120v2)), SAM-mask lifting into collision geometry ([3DGS twin](https://arxiv.org/html/2601.03200v1)), and metric-scale twins aligned with ArUco markers ([GSWorld](https://arxiv.org/pdf/2510.20813v1)). The research found **no published image → terrain → legged RL pipeline**. The practical design is therefore a VLM call that maps a photo to a terrain class plus parameters ("gravel slope, about 15°, low friction"), which goes through the same schema and validator. The open niche is adversarial generation. LLM red-teaming of robots so far targets instructions for language-conditioned policies, as in ERT ([ERT](https://arxiv.org/abs/2411.18676v2)) and Q-DIG, which combines quality-diversity search with VLMs ([Q-DIG](https://arxiv.org/html/2603.12510)). It also covers driving scenarios, where fine-tuning on ChatScene's adversarial scenarios cut collisions by about 9% ([ChatScene](https://arxiv.org/html/2405.14062v1)). Non-LLM geometric red-teaming dropped real manipulation success from 90% to as low as 22.5% ([GRT](https://arxiv.org/html/2509.12379v1)), which shows how much damage targeted physical scenarios can do. A legged-robot "LLM red team" fits the existing schema directly. The model proposes a scenario. The simulator returns structured metrics (fell, time-to-fall, max tilt, slip). The model then proposes harder or more diverse variants, and failures go into a grid indexed by terrain type and dominant stressor (`dominant_stressor()` already computes the latter).

## Budgeted black-box search finds the worst case; MAP-Elites maps the territory

Failure search methods fall into four families, each with a different cost profile on a CPU.

| Family | Representative 2023-2026 work | What it finds best | CPU cost |
|---|---|---|---|
| Black-box optimizers (CEM, CMA-ES, BO) over θ | CEM falsification lineage; multi-fidelity BO ([2409.08097](https://www.arxiv.org/pdf/2409.08097)) | Worst-case or minimal static scenario | Hundreds to low thousands of rollouts |
| Quality-diversity (MAP-Elites) | QD terrains for Cassie/ANYmal ([2506.01362](https://arxiv.org/abs/2506.01362)) | Many *distinct* failure modes | Similar to CEM; about 100 lines of numpy |
| Adaptive stress testing (MCTS/RL over sequences) | AST ([JAIR](https://jair.org/index.php/jair/article/download/12190/26631)) | Most-likely failure path | Moderate to high |
| Learned RL adversaries | Shi et al. RSS 2024 ([2405.12424](https://arxiv.org/abs/2405.12424)); H-infinity ([2404.14405](https://alphaxiv.org/abs/2404.14405)) | Time-varying, state-dependent attacks | About one training run |

For a small project, the first two families should be built first. CEM over θ is trivially parallel across processes and has a long falsification record. Sankaranarayanan and Fainekos showed that CEM guided by a continuous trace-robustness score found violations faster and more consistently than competing methods ([ASU](https://asu.elsevierpure.com/en/publications/falsification-of-temporal-properties-of-hybrid-systems-using-the-/)). That continuous score is the key implementation detail. The optimizer needs a graded signal, such as minimum base-height margin, maximum roll or pitch margin, or time-to-fall, not a binary "fell" flag. The objective should also subtract a penalty on scenario magnitude, so that the search returns *minimal* failures rather than trivially huge pushes. This mirrors the cost constraints that H-infinity locomotion and Zhang et al.'s "critical attack" humanoid work put on their adversaries ([Zhang et al. 2025](https://arxiv.org/html/2507.08303v1)). `Scenario.severity()` is already that penalty. A failure found at severity 0.2 is a more damning finding than one at 0.9, and the report should rank failures that way.

Optimizers converge on one failure mode. MAP-Elites instead keeps the hardest scenario in each cell of a descriptor grid (for example push direction × friction, or roughness × step height), so it covers *types* of failure. The 2025 QD-terrain work built a 930-terrain archive for Cassie and ANYmal controllers. That archive exposed qualitatively different failures, such as heading drift on narrow platforms and leg-trapping obstacles, and was then used to improve the controllers ([QD terrains](https://arxiv.org/abs/2506.01362); [review](https://www.themoonlight.io/review/generating-diverse-challenging-terrains-for-legged-robots-using-quality-diversity-algorithm)). Earlier work found MAP-Elites beat Monte Carlo and optimization methods at covering failure-scenario space ([Fontaine & Nikolaidis](https://ar5iv.labs.arxiv.org/html/2012.04283)). QD has two weaknesses: it handles noisy evaluations poorly, and a badly chosen descriptor hides the dynamics that matter ([Flageat & Cully et al.](https://arxiv.org/pdf/2305.01264)). The fix is to re-evaluate each elite with several seeds before admitting it.

Two further features are worth adding because they target blind spots. First, parameter sweeps miss *sequential low-magnitude* attacks. Shi et al. showed that state-of-the-art robust quadruped controllers fail significantly under small, well-timed perturbations of observations and commands ([Shi et al.](https://arxiv.org/abs/2405.12424)). A bounded observation-noise adversary therefore belongs in the suite even before any learned adversary. On a CPU, a cheap version is CEM over a short piecewise-constant noise schedule rather than a trained network. Second, sample efficiency improves sharply once failures are rare. DeepMind's learned failure-probability predictor over initial conditions found humanoid-locomotion failures with **about 3,100x fewer samples than random testing** ([Rigorous Agent Evaluation](https://arxiv.org/html/1812.01647)). Dawson and Fan's Bayesian-inference framing reported a more diverse failure set in **up to 2x fewer iterations** than gradient-free search ([PMLR](https://proceedings.mlr.press/v229/dawson23a.html)). A small classifier (logistic regression or gradient-boosted trees on θ) trained on every rollout the platform has ever run is a cheap way to capture the first effect: it ranks candidate scenarios before they are simulated. Multi-fidelity BO adds a CPU-friendly trick. It chooses both the test input and the simulator fidelity, which beat full-fidelity BO on Gym tasks ([Shahrooei et al.](https://www.arxiv.org/pdf/2409.08097)). In MuJoCo, "low fidelity" can simply mean a shorter horizon or a coarser timestep for screening, with full rollouts reserved for confirming candidates.

## Margins need bisection per direction and gait phase, not a single push

The field's most common scalar margin is the **maximum recoverable push impulse**, and how it is measured matters. The Cassie sim-to-real work ran a line search per direction, with a 0.2 s impulse at the pelvis and a 3.0 s recovery window, and averaged across directions ([Cassie](https://arxiv.org/pdf/2204.04340)). A biped whole-body-control paper ramped the impulse in fixed steps and found that pushes at certain phases are hardest, because recovery takes about a full swing duration ([2109.07196](https://arxiv.org/pdf/2109.07196)). Quadruped stabilization likewise depends on the instantaneous gait phase ([2503.10401](https://arxiv.org/pdf/2503.10401)). Results are now reported as relative gains in this metric. For example, a humanoid hierarchical-MPC paper reports a 131% average improvement in maximum recoverable impulse ([2409.14342](https://arxiv.org/html/2409.14342v3)). No standard fixes push duration, application point or recovery window yet. ASTM F45.06 has proposed WK86916, a disturbance-rejection test method for legged robots, but it is a work item, not a published standard ([ASTM](https://www.astm.org/news/stability-performance-legged-robots-so23)).

The implementable protocol follows from this. For each of 8 directions and 4 gait phases, bisect the impulse magnitude over about 8 steps, with 3 seeds per probe and majority-vote success. That is roughly **770 short rollouts per policy**. The outputs are a polar plot plus two headline numbers: the worst-direction margin and the mean margin. One change to the existing schema is needed. `Push.t` is in seconds after start, so phase must be controlled by triggering the push on a contact event (for example, the front-left foot's touchdown plus an offset), not by wall-clock time. Push duration and application body should be fixed and printed on the report, because without a standard these choices are what make numbers comparable across policy versions.

Pushes are one axis. For every other `BOUNDS` field (friction, payload, payload offset, motor strength, latency, sensor noise, slope, step height), the platform should sweep one factor at a time. At each sweep point it records the success rate and the velocity-tracking error, then bisects for the **50% and 90% breaking points**. Velocity under stress is a meaningful second metric. In one humanoid study, standard DR reached **0.00 m/s under unmodeled actuator stiffness, against 0.36 m/s** for joint-torque perturbation injection ([2504.06585](https://arxiv.org/pdf/2504.06585)). This makes "still walks" and "still survives" different claims. On 2D slices (friction × push, payload offset × slope), the platform should draw the failure frontier by bisecting along rays from the nominal point. Bisection assumes failures are monotone, and gait-phase effects break that assumption, so random or CEM probes should also be run *inside* the region labelled safe to catch islands of failure. Finally, worst-case margins should be paired with a probabilistic one: the estimated failure probability under a declared deployment prior over θ. Bayesian Safety Validation frames this as one of the three core validation tasks, alongside falsification and most-likely failure ([BSV](https://pdf.arxiv.org/pdf/2305.02449)).

## Hardening must replay failures, bound the adversary and test on held-out attacks

Feeding failures back into PPO works, but the published evidence carries a warning that should shape the platform's design. Fine-tuning on Shi et al.'s adversarial scenarios "notably" improved robustness, including to sensor noise and external pushes. Yet **the controllers stayed vulnerable to attack spaces that were not targeted** ([Shi et al.](https://arxiv.org/abs/2405.12424); [review](https://www.themoonlight.io/review/rethinking-robustness-assessment-adversarial-attacks-on-learning-based-quadrupedal-locomotion-controllers)). The hardening loop should therefore always end by re-running the same search *and* a held-out attack family the training never saw. One way to set this up: if training replays push and friction failures, evaluate on latency and observation-noise attacks too. A policy that improves only on the replayed family has overfit to its own adversary.

The second design constraint is that the adversary must stay bounded. Every successful 2024-2026 method limits attack strength. The H-infinity disturber constrains the ratio of its cost to the force it applies, which keeps joint training stable, and the policy transferred to real Unitree robots ([H-infinity](https://mlanthology.org/corl/2024/long2024corl-learning)). The humanoid "critical attack" work constrains attacker cost so that attacks improve robustness instead of destroying performance ([Zhang et al.](https://arxiv.org/html/2507.08303v1)). HORIZON (2026) widens randomization only within the policy's current recoverable boundary and rolls back to a checkpoint after an unrecoverable step. It reports that widening past the frontier can collapse training ([HORIZON](https://arxiv.org/html/2606.05143)). Curriculum research adds a behavioural hazard. ACCEL reached nearly **3x the best baseline on BipedalWalker** by editing high-regret levels, but also observed that overly hard levels push agents toward a "don't fall" local optimum instead of walking forward ([ACCEL](https://ar5iv.labs.arxiv.org/html/2203.01302)).

These findings combine into a concrete CPU recipe. A fine-tuning batch is sampled from three sources: about 50% nominal DR, 30% PLR-style replay of discovered failures prioritized by failure score, and 20% newly widened DR. Two filters apply to replay. Failures above the current recoverable boundary are held back until the margin sweep shows the policy can reach them. Replay is also capped by `severity()`, so the buffer is not dominated by unlearnable scenarios. This split is a synthesis of the methods above, not a tuned published ratio. The hardened policy should only be accepted if nominal velocity-tracking error has not regressed beyond a tolerance, which guards against the ACCEL failure mode.

The PPO side should copy hardware-proven settings rather than tune from scratch. The legged_gym/rsl_rl defaults are γ 0.99, λ 0.95, clip 0.2, 5 epochs × 4 minibatches, and learning rate 1e-3 with an adaptive-KL schedule targeting 0.01. They also use entropy 0.01 and ELU [512,256,128] networks ([legged_gym config](https://raw.githubusercontent.com/leggedrobotics/legged_gym/master/legged_gym/envs/base/legged_robot_config.py)). The adaptive schedule matters most here, because it removes the need for learning-rate sweeps that a CPU budget cannot afford. MuJoCo Playground's Go1 recipe adds two nearly free sample-efficiency features: running observation normalization, and an **asymmetric critic** whose privileged state includes the applied push force and a perturbation-active flag ([Playground 0.2.0](https://pypi.org/project/playground/0.2.0/)). For a robustness platform, this privileged channel should carry every θ component (true friction, payload, motor strength, latency), because the critic can then attribute value drops to the stressor that caused them. The same Playground recipe uses **200M steps across 8192 environments** on a GPU ([Playground 0.2.0](https://pypi.org/project/playground/0.2.0/)). That scale is out of reach on a CPU, which is why the platform's training jobs should be short fine-tunes from a nominal checkpoint, not fresh runs.

The action space matters for both speed and robustness. The existing `world.py` uses raw torque motors. Instead, the policy should output PD targets around the nominal pose, as in Playground (`target = default_pose + 0.5·action`), with torques computed in Python and clipped to `TORQUE_LIMIT × motor_strength`. A residual-over-CPG option is worth adding as a second action space for one reason specific to this platform: latency robustness. Under 90 ms of delay, CPG policies on a Go1 kept **55-71% success while joint-space baselines failed completely** ([Visual CPG-RL](https://arxiv.org/abs/2212.14400v2)), and `latency_steps` is one of the schema's stress axes. Evidence that CPG priors improve *sample efficiency* is mixed ([2410.16417](https://arxiv.org/html/2410.16417v1)), so the CPG option should be justified on robustness grounds, not speed. One performance detail matters for the search loop. `build_xml` bakes friction into the MJCF, so every search candidate currently forces a model rebuild. Compiled models should be cached by terrain parameters, and friction, mass, payload and gains should be mutated in place through `model.geom_friction`, `model.body_mass` and `actuator_gainprm`, in the same way the Playground and walk-these-ways DR code randomizes them ([walk-these-ways](https://raw.githubusercontent.com/Improbable-AI/walk-these-ways/master/go1_gym/envs/go1/go1_config.py)).

## Readiness reports should certify with confidence bounds and disclose search budget

No agreed deployment-readiness standard exists for learned locomotion. ASTM's legged-robot work is still at the proposal stage ([ASTM](https://www.astm.org/news/stability-performance-legged-robots-so23)), and no published certification threshold (such as a minimum impulse) was found. In practice, labs gate hardware deployment on a **sim-to-sim transfer check**: train in Isaac Gym or Lab, evaluate zero-shot in MuJoCo, then deploy ([RoboDreamer](https://arxiv.org/pdf/2609.07096)). Simulator settings can mislead that check in both directions. A zero-armature setting used in Isaac Gym training caused failure in MuJoCo ([2607.11624](https://arxiv.org/pdf/2607.11624)), and tuned MuJoCo friction can make a policy look smoother without making it more robust ([2512.18938](https://arxiv.org/pdf/2512.18938)). A single-simulator CPU project can still run a meaningful proxy by re-running the scorecard under a perturbed simulator configuration (armature, contact solver parameters, timestep, integrator) and reporting the change in each metric.

The report itself should be a fixed scorecard, generated as JSON plus a rendered HTML or Markdown page. Every row states its sample size, and every adversarial row states its search budget.

| Section | Metric | How it is computed | Pass rule (set per deployment) |
|---|---|---|---|
| Nominal | Success rate; linear and yaw velocity RMSE over a command grid | Fixed seeds, full episodes | Tracking error under a stated tolerance |
| Push margin | Worst-direction and mean max recoverable impulse | 8 directions × 4 phases bisection | Worst-direction ≥ the deployment requirement |
| Parameter margins | 50% and 90% breaking points per stressor | One-factor bisection | Each breaking point outside the deployment envelope |
| Adversarial | Failures found by CEM, MAP-Elites, obs-noise adversary within severity ≤ B | Fixed rollout budget, reported | "None found in N rollouts at severity ≤ B" |
| Probabilistic | Failure probability under the deployment prior, with 95% upper bound | Monte Carlo plus Clopper-Pearson | Upper bound below target |
| Sim-to-sim | Change in all of the above under a perturbed simulator config | Re-run of the suite | No metric degrades past tolerance |
| Regression | Diff against the previous policy version on the accepted-scenario library | Replay | No previously passing scenario now fails |

Two statistical rules keep the report honest. First, falsification can show that a failure exists but never that none does, so "no failure found" means nothing without the rollout count and the severity bound searched. This is why the black-box validation literature treats falsification, most-likely failure and failure-probability estimation as separate tasks ([Corso et al. survey](https://arxiv.org/pdf/2005.02979)), and why the report needs rows for all three. Second, zero failures in N Monte Carlo trials still leaves a 95% upper bound of about 3/N on the failure probability (the "rule of three"). The report should state this upper bound directly, because "0 failures in 200 runs" reads as perfect but only certifies a rate below about 1.5%. The visuals that best support a go/no-go decision are the failure frontier and the MAP-Elites atlas, drawn before and after hardening. They show at a glance whether fine-tuning moved the boundary, shrank one region while another grew, or only fixed the replayed family, which was Shi et al.'s finding.

The build order follows from cost and dependency. Schema validation and the offline parser come first, since they already largely exist. Next come the margin sweeps, which also produce the grounded parameter ranges the LLM generator needs, then CEM search with the severity penalty, then the MAP-Elites atlas. PPO replay fine-tuning follows, with held-out evaluation. The readiness report is generated from artifacts that all earlier stages already write. The LLM red-team loop and image input come last, because they are only as trustworthy as the validator and search harness underneath them.

## Conclusion

The literature changes what counts as the hard part. Generating scenarios from language or images is now routine, but only once the output space is constrained and grounded: about half of free-form terrain code fails, and LLM ranges beat uniform sampling only inside empirically measured bounds. Finding failures is cheap. The hard part is failing *usefully*: minimal failures ranked by severity, diverse failures rather than one mode, and adversaries bounded so that training does not collapse or settle into standing still. The research also points to a structural risk. Every hardening loop overfits to the adversary that drives it, so the held-out attack family and the before/after frontier are what separate real robustness from robustness to the platform's own tests.

For a small CPU project, this is an advantage rather than a limitation. Its value lies in the rigor and transparency of the evaluation loop: grounded bounds, phase-controlled margins, stated search budgets and confidence intervals. None of these depend on compute. The clearest opportunity to contribute something new is the LLM as an adversary over physical locomotion scenarios, archived in a quality-diversity grid. The research found no prior work on it, and the existing schema makes it a few hundred lines rather than a research program. The main unknown is quantitative: no source compares search methods head-to-head on one locomotion policy, so the platform's own logs from searches run on the same policy could produce the first such comparison.
