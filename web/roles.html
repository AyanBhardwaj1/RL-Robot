Controls and motion planning

Whole-body control, balance and stepping, MPC, state estimation; real-time C++ and Python.

In Breakpoint

  • breakpoint/humanoid.py: linear-inverted-pendulum balance with capture-point stepping, bounded by ankle torque, friction, swing time, leg reach and lateral reach, with slope compensation by leaning.
  • Measured: the biped survives 92 N·s from the front but only 44 N·s from the side, because while one foot swings only the other carries weight. 150 ms of lag, compensated by a Smith predictor, still cuts the front limit to 57 N·s. A 20 kg tote held in front drops forward pushes from 92 to 77 N·s.
  • Wheeled-base model that drives under its capture point: 137 N·s from the front and 120 from the side, but blocked by any curb over 2.5 cm.
  • A live capturability map, built from 1,369 simulations per redraw, colours every shove by the steps it needs. It exposed a bug in my own latency model that bisection could not see; the fix is in all three implementations.
  • The controller respects the friction cone like a balance QP would, and a failure is blamed on the floor only if ample grip would have saved it; 15 of 16 trailer “slips” were really falls.
  • breakpoint/design.py: which spec change helps most, paired on 750 shifts. A 15% faster swing saves 24 and loses none (p < 0.001); +25% ankle torque saves none, because the foot is the limit.

Next I’d build

A QP whole-body controller on a MuJoCo humanoid that tracks the same capture-point steps, so the reduced model can be checked against full dynamics.

Simulation

MuJoCo and Isaac environments, contact models, domain randomization, sim-to-real, MJCF/URDF tooling.

In Breakpoint

  • world.py builds a 12-joint quadruped and heightfield terrain (rough, slope, stairs) procedurally in MJCF; env.py adds PD actuation, latency, sensor noise, pushes at exact gait phases.
  • One validated scenario schema clamps every input, whether typed, photographed, generated by an LLM or proposed by search.
  • An independent review caught mirrored push directions; a physical regression test now pins the convention.

Next I’d build

System identification from logged hardware runs, fitting friction, actuator lag and torque limits so the scenario bounds come from the robot rather than defaults.

Robot learning

RL and imitation learning for locomotion and manipulation, foundation and VLA models, sim-to-real.

In Breakpoint

  • PPO with hand-written backprop in numpy (checked against finite differences), trained on one CPU core in about 4 minutes.
  • Hardening loop: failures are found, shrunk to minimal tests, replayed in training; a checkpoint ships only if it beats the start.
  • Honest results: one round took readiness 76.5 → 82.6; a second round overfit; latency could not be trained away, so a latency gate took teleop failures from 10% to 0%.

Next I’d build

Use the same audit as an evaluation harness for a learned manipulation policy: grasp success versus tote mass, friction and sensor delay.

ML systems and edge deployment

Profiling, quantizing and distilling policies to fit onboard compute; ONNX/TensorRT; latency budgets.

In Breakpoint

  • quantize.py: FP16 and per-channel INT8 compression with a robustness check, not just an action-error check.
  • Measured: INT8 is 3.6× smaller (32.3 KB → 9.1 KB) with mean action error 0.002, and readiness unchanged at 84.1 with 0% teleop failures.
  • The FP16 run scored 84.8: a 10⁻⁴ action change moved bisection edges, so the score has about ±0.7 of noise worth reporting.

Next I’d build

ONNX export with a real INT8 runtime, and a CI gate that fails when a compressed policy’s breaking point on any axis drops below a set margin.

Real-time and embedded

Real-time C++ control loops, EtherCAT and CAN, motor drives, firmware, latency.

In Breakpoint

  • Control latency is modelled at the step level: 20 ms per control tick in the quadruped, continuous in the humanoid.
  • Measured latency budgets: the gated policy tolerates 120 ms; ungated learned policies fail above 40–60 ms.
  • Actuator strength is an axis: the best quadruped policy keeps walking at 21% of nominal torque.
  • cpp/capture_point.hpp: a header-only C++17 controller with an allocation-free 2 ms step(), matching Python to 0.01 N·s on all 16 breaking points (tested in CI with -Werror).
  • 500 Hz benchmark: the step costs 0.8 µs (p50) to 1.7 µs (p99), but wake-up jitter on a stock kernel reaches 4.9 ms, more than two missed periods. The case for PREEMPT_RT, measured.

Next I’d build

The same loop on a PREEMPT_RT kernel with an isolated core and SCHED_FIFO, with jitter fed back into the humanoid lab as a latency distribution.

Platform and developer tools

Fleet and integration

Fleet software, APIs to warehouse and plant systems, monitoring, uptime.

In Breakpoint

  • Deployment profiles turn a site into a distribution of conditions; failure odds come with a 95% upper bound and causes.
  • A stateless HTTP API (/api/simulate, /api/deploy, /api/probe) with validation, size caps and caching.
  • Humanoid job odds: biped 0% vs wheeled 47% on home-care routes (stairs), wheeled 16% on trailer unloading (lips and debris).
  • fleet.py: fits a site profile from per-shift telemetry (JSON Lines) using robust quantiles. A deliberately glitched sensor doesn’t move it. It then re-runs the odds for both bodies; on 300 synthetic shifts it recovers the true payload, friction and contact rate.

Next I’d build

Drift alerts: compare tonight’s fitted profile with last week’s and flag when the odds move past their confidence bounds.

Test and validation

Hardware-in-the-loop and simulation tests, regression suites, coverage, release gates.

In Breakpoint

  • Shrunk counterexamples saved as JSON with seeds; regress replays them on 3 seeds and exits non-zero on failure.
  • certify writes a certificate with the policy’s SHA-256, toolchain versions and git commit, and fails CI below a score.
  • Compound stress: two stresses that each pass alone at 75% of their limits can fail together.

Next I’d build

The same suite runner against a hardware-in-the-loop target, with the simulator and the bench sharing one scenario file.

Safety

Hazard analysis, functional safety (IEC 61508, ISO 13849, ISO 10218), safety for learned systems.

In Breakpoint

  • Every failure rate carries a 95% upper bound, and every report states its search budget: no failure found is not proof of none.
  • Failures are explained from evidence, for example “fell 0.7 s after a 12 N·s shove from the right with slippery ground and a 3 kg payload”.
  • Biped versus wheeled odds by job make the stability trade-off explicit.
  • hazards.py: every failure class becomes a hazard log entry with a measured frequency and 95% bound, severity, a 4×4 risk rating, mitigation and the command that re-verifies it. Top entry: wheeled base blocked on 47% of home-care routes.

Next I’d build

Trace each hazard to a requirement and a regression scenario, so a code change that raises a hazard’s measured rate fails CI.
